# DrainWatch

Automated drainage blockage detection for UK Environment Agency flood defence
webcams, built as part of an MSc dissertation. A CNN classifier periodically
checks public flood-camera feeds across Devon and Cornwall, flags likely
blockages, and surfaces them on a live operations dashboard — with
Grad-CAM visual explanations, an LLM-generated natural-language write-up for
each flagged case, and a human-in-the-loop correction system so operators can
fix mistakes without retraining the model.

## What it does

- **Continuous monitoring** — a scheduled sweep (every 15 minutes by default)
  pulls the latest frame from each configured webcam and classifies it as
  Clear, Blocked, or Needs Review.
- **On-demand analysis** — upload any image, or trigger an immediate check of
  a specific camera, outside the regular sweep.
- **Interpretability** — every Blocked/Needs Review result includes a
  Grad-CAM heatmap plus a short natural-language explanation generated by an
  LLM (Cerebras), grounded in the heatmap rather than the raw prediction
  alone.
- **Correction memory** — when an operator manually marks a result as
  Blocked/Clear, that correction is stored (as a frozen-backbone embedding,
  scoped per camera) and trusted on future near-duplicate frames of the same
  scene, without ever touching the trained model's weights. See
  `app/correction_memory.py` for why this approach was chosen over
  online fine-tuning.
- **Operations dashboard** ("Flood Watcher") — a live map of every camera,
  suggested inspection routes clustering nearby blockages, a Needs Review
  queue, and one-click PDF incident reports.

## Live demo

A live instance of this system is deployed and continuously monitoring
real cameras. It's not publicly listed here since access is protected by
Basic Auth — available on request.

## Architecture

```
                 ┌─────────────┐
  Internet ───▶  │    Caddy    │  HTTP Basic Auth, :8443
                 │ (reverse    │
                 │  proxy)     │
                 └──────┬──────┘
                         │
            ┌────────────┴────────────┐
            │                         │
      ┌─────▼─────┐            ┌──────▼──────┐
      │  backend   │            │  frontend    │
      │  FastAPI   │◀──REST────│  Flood       │
      │  + APScheduler         │  Watcher     │
      │  + SQLite  │            │  (TanStack   │
      └────────────┘            │   Start/     │
                                 │   React)     │
                                 └──────────────┘
```

All three run as separate Docker Compose services. Only the proxy is exposed
to the internet; the backend and frontend are reachable exclusively through
it.

## Quick start (Docker, recommended)

Requires Docker and Docker Compose.

```bash
git clone https://github.com/gseira/drainage-blockage-detection.git
cd drainage-blockage-detection
cp .env.example .env        # add your own Cerebras API key (see below)
```

You'll also need the trained model checkpoint — it's not in this repo
(hundreds of MB of binary weights). Place it at:

```
results/checkpoints/best_model.pt
```

Set a Basic Auth password for the proxy:

```bash
docker run --rm caddy:2-alpine caddy hash-password --plaintext 'your-chosen-password'
```

Paste the resulting hash into `Caddyfile` in place of the placeholder, then
bring everything up:

```bash
docker compose up -d --build
```

The app is now reachable at `https://localhost:8443` (or your server's
address if deployed remotely), behind the Basic Auth login you just set.

## Quick start (local development, no Docker)

Requires Python 3.10+ and Node.js 18+.

**1. Install backend dependencies**

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

**2. Install frontend dependencies**

```bash
cd "Flood Watcher"
npm install
cd ..
```

**3. Set up your API key**

```bash
cp .env.example .env
```

Edit `.env` and add your own Cerebras API key (free tier available at
[cloud.cerebras.ai](https://cloud.cerebras.ai)). The app still runs without
one — it just shows a placeholder instead of a full explanation for flagged
results.

**4. Add the model checkpoint** — see above; place it at
`results/checkpoints/best_model.pt`.

**5. Run both parts, in two terminals**

```bash
# Terminal 1 — backend
uvicorn app.main:app --reload --port 8000
curl http://127.0.0.1:8000/health   # sanity check once it's up

# Terminal 2 — frontend
cd "Flood Watcher"
npm run dev
```

Open the URL the frontend prints (usually `http://localhost:3000`).

## Configuration

| Variable | Purpose | Default |
|---|---|---|
| `CEREBRAS_API_KEY` | Enables LLM-generated explanations for flagged results | none (explanations fall back to a placeholder) |
| `CHECKPOINT_PATH` | Path to the model checkpoint | `results/checkpoints/best_model.pt` |
| `DB_PATH` | SQLite database location | `monitoring.db` in project root |
| `MONITOR_INTERVAL` | Minutes between automatic sweeps | `15` |

## API overview

| Endpoint | Description |
|---|---|
| `GET /health` | Liveness check |
| `GET /webcams` | List of configured cameras |
| `POST /predict` | Classify a single uploaded image |
| `POST /predict/batch` | Classify multiple uploaded images |
| `POST /predict/webcam` | Fetch and classify a camera's current frame |
| `GET /results/latest` | Most recent result per camera |
| `GET /results/history` | Time-filtered result log |
| `GET /results/stats` | Daily Blocked/Clear counts |
| `POST /results/reclassify` | Record a manual correction (Mark Blocked/Clear) |

## Notes on the model

Held-out validation metrics on this dataset are optimistic (near-duplicate,
same-scene frames leak between train/val splits for these fixed cameras) and
should not be read as real-world accuracy. The evaluation scripts in
`risk_assessment/` implement a stricter live-pair validation methodology
instead — comparing predictions on genuinely independent captures of the
same scene — which is what the dissertation's evaluation chapter is based
on. See the module docstrings in `app/correction_memory.py` and
`models/finetune_problem_cameras.py` for the reasoning behind design choices
that aren't obvious from the code alone (several were the result of
production mistakes, documented rather than hidden).

## Data source

Webcam imagery is drawn from the Environment Agency's public Flood Defence
Camera Network (`eacornwallwebcams.org` / `eadevonwebcams.org`). This project
does not redistribute any of that imagery — only the code that fetches and
classifies it live.
